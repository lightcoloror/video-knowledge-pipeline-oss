# Trusted Capability Tunnel Entry Wrapper Source Guide

## 1. Purpose and Scope
This document specifies the operational contracts for the first-party VKP secure tunnel wrappers (`scripts/start-trusted-capability-tunnel.ps1` and `scripts/start-trusted-capability-tunnel-8081.ps1`) under the AGPL-3.0-only license. The wrappers parameterize optional secure-client launching, Windows DPAPI credential caching, and the port 8081 operational alias without bundling upstream tunnel client binaries, YAML profiles, or access credentials.

## 2. Parameter Resolution and Execution Guards
The updated launcher introduces explicit parameter and environment bindings while preserving original switch positions:
- **Client and Profile Binding**: In normal execution, `$client` and `$profile` must be provided via `-ClientPath` and `-ProfilePath` or through process environment variables `VKP_TUNNEL_CLIENT_PATH` and `VKP_TUNNEL_PROFILE_PATH`. Missing-path guards execute strictly after `-CredentialStatus` and `-ForgetCredential` early exits, allowing status checks and credential clearing without requiring external binary paths.
- **Credential Storage**: `-CredentialDirectory` accepts an explicit argument or environment override (`VKP_TUNNEL_CREDENTIAL_DIRECTORY`), falling back to project-local `.local\tunnel-client\secrets`.
- **8081 Alias Wrapper**: Resolves `$runtimeDirectory` via `VKP_TUNNEL_RUNTIME_DIRECTORY` or local default, creates the directory, sets health-listener, log and PID environment variables, and forwards `@args` unchanged.

## 3. Governance and Verification Limits
- **Credential and Transport Boundaries**: Retains Windows DPAPI (`Export-Clixml`) and the original current-user ACL setter; actual permissions were not verified. The presence of these functions does not constitute cryptographic or operational security verification. A binary path named `verified` does not imply binary trust.
- **Verification Status**: Both scripts remain strictly **UNEXECUTED (NOT RUN)**. Static text/delta review and two non-executing Parser.ParseFile checks in the current PowerShell 7.5.2 host completed with zero parse errors. No target script, DPAPI/ACL function, credential operation or client was run. Upstream client signatures, DPAPI behavior, and endpoint connectivity are unverified.

Original credential/ACL function bodies are byte-identical; the first two switch positions and alias forwarding/environment restoration remain unchanged in source. Static parameter parsing is not runtime parameter binding, PowerShell 5.1 compatibility, filesystem ownership or operational security proof. Explicit paths are operator selections, not an OS sandbox. A credential-directory override can move the saved file and deletion target outside the project; it is used as supplied without an additional whitespace/absolute-path constraint. The original ACL setter targets the temporary credential file, not the containing directory. CredentialStatus checks existence, not decryptability or security. The alias creates its runtime directory even when forwarding status/forget. AGPL-3.0-only covers this first-party wrapper increment, not an unprovided client, profile or credential. Source release grants no authorization to execute credential deletion, storage, ACL changes or client startup. The earlier blocked harness was not rerun, and no execution-policy or host change was made for this static read.
